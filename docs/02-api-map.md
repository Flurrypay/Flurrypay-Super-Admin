# API map

Source: inspection of `api/src/app/routes`, `controllers`, `services` and `api/src/core/middlewares`. Rows marked **(branch)** describe behaviour on the API branch `admin-console-hardening`, which the console targets; see `api/docs/admin-console-hardening.md`.

## Transport and conventions

| Aspect            | Behaviour                                                                                                                                                                                                                                                                                                                                                                                                                                                                    |
| ----------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Base paths        | Admin routers are mounted under obscured prefixes: `/flurrypay-website-admin`, `-wallet`, `-notifications`, `-swap-history`, `-tracker`, `-financial`, `-compliance`, `-risk`, `-stranded`, `-ledger`, `-support`, `-careers`, `-chat`. Some admin endpoints live on shared routers: `/user/*`, `/kyc/admin/*`, `/transactions/admin/*`, `/company-details/*`, `/trade-queue/admin/*`, `/campaigns/admin/*`, `/govt-id-photos/*`, `/payment/*`. `/admin` itself returns 404. |
| Admin guard       | `adminBotGuard` returns **404** (not 401/403) for blocked IPs, empty or known-bot user agents, and, in production, `Origin`/`Referer` values that don't contain `flurrypay.io` or `localhost`.                                                                                                                                                                                                                                                                               |
| CORS              | Allowed origins: `https://flurrypay.io`, `https://www.flurrypay.io`, `https://api.flurrypay.io`, plus localhost ports 3000/5173/8081 outside production. `credentials: true`. Allowed request headers: `Content-Type, Authorization, X-Requested-With, X-Request-ID, ClientID, Accept, Origin, Cache-Control`. `X-Request-ID` is exposed.                                                                                                                                    |
| Request ID        | The API generates `X-Request-ID` per request and returns it; error bodies from the global handler include `requestId`.                                                                                                                                                                                                                                                                                                                                                       |
| Versioning        | None.                                                                                                                                                                                                                                                                                                                                                                                                                                                                        |
| Response envelope | Inconsistent across routers: `{ success, data, … }`, `{ status: false, message }`, `{ message, admin }`, bare arrays (`GET /flurrypay-website-admin/users`) and bare objects. The admin UI validates each endpoint with its own Zod schema.                                                                                                                                                                                                                                  |
| Error shape       | `{ message, code? }` for auth failures (see codes below); `{ success: false, message }` elsewhere.                                                                                                                                                                                                                                                                                                                                                                           |
| Pagination        | Three styles: `page`/`limit` with a `pagination` object (`/transactions/admin/all`); `limit`/`offset` with `total` (`/…-financial/audit-logs`); **none** (users list, KYC list, admin list).                                                                                                                                                                                                                                                                                 |
| Money in JSON     | Decimals are serialised as JS numbers (entity transformers), so `decimal(20,8)` values may lose precision.                                                                                                                                                                                                                                                                                                                                                                   |

One session per admin: a new login invalidates the previous token (`sessionId` check). Super admins are exempt from device binding.

### Step-up middlewares

These read their credentials from the JSON body:

| Middleware                  | Body field       | Failure codes (HTTP 401 unless noted)                                                                     |
| --------------------------- | ---------------- | --------------------------------------------------------------------------------------------------------- |
| `verifyAdminPassword`       | `password`       | `ADMIN_PASSWORD_MISSING`, `ADMIN_PASSWORD_INVALID`                                                        |
| `verifyAdminTransactionPin` | `pin` (6 digits) | `ADMIN_PIN_MISSING`, `ADMIN_PIN_NOT_SET`, `ADMIN_PIN_INCORRECT`, `ADMIN_PIN_LOCKED` (5 attempts → 15 min) |
| `verifyAdmin2FA`            | `twoFACode`      | `ADMIN_2FA_NOT_ENABLED` (403), `ADMIN_2FA_CODE_MISSING`, `ADMIN_2FA_INVALID`                              |

These failures use **HTTP 401**, the same status as an expired session. The admin client distinguishes them by `code` and never signs the admin out on a step-up failure.

## Authorization model

- Roles: `admin`, `executive`, `superAdmin` (`AdminRole`). `executive` has no distinct server-side behaviour.
- Permissions: 13 values (`AdminPermission`), 12 grantable to staff; `wallets.withdraw` never is. **(branch)** adds `treasury.view` and `compliance.review`. Super admins bypass all checks.
- **(branch)** Custom roles (`admin_roles`) are named permission sets. Assigning one copies its permissions to the admin and records `customRoleId`; editing the role updates every staff admin assigned to it.
- Enforcement before the branch: `isSuperAdmin` on admin management and a few money routes, `requirePermission(wallets.withdraw)` on 6 routes, nothing else.
- **(branch)** Every admin route carries `requirePermission(...)` or `isSuperAdmin`. Only self-service routes (own details, 2FA, PIN, recovery codes, session refresh, logout, global search) are token-only.
